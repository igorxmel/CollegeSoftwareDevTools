# ПЗ №17. Шаблоны элементов в React

Приложение на React, которое переключает светлую и темную тему через Context API. На странице три карточки: одна повторяет глобальную тему, вторая всегда остается светлой, третья показывает тему, противоположную странице.

Состояние темы вынесено в `ThemeContext.jsx`. Там лежат сам контекст, провайдер и хук `useTheme`, поэтому компонентам не нужно передавать тему через промежуточные props. `App.jsx` собирает страницу: заголовок, кнопку переключения и три карточки. `ContentCard.jsx` отвечает только за то, какую тему показать внутри карточки, а цвета описаны CSS-переменными в `index.css` и `ContentCard.css`.

Проект собран на Vite. В `package.json` три скрипта: `dev` запускает сервер разработки, `build` собирает production-версию, `preview` показывает собранную версию локально.

## Как устроен контекст

Контекст создается с значениями по умолчанию:

```jsx
export const ThemeContext = createContext({
    theme: "light",
    toggleTheme: () => {}
});
```

Значения по умолчанию нужны на случай, если компонент обратится к контексту вне провайдера. Тогда он получит `light` и пустую функцию, а не ошибку. В этом приложении провайдер стоит выше всего дерева, поэтому все компоненты видят настоящее состояние.

Провайдер хранит тему в `useState` и передает вниз два значения: саму тему и функцию переключения:

```jsx
export const ThemeProvider = ({ children }) => {
    const [theme, setTheme] = useState("light");

    const toggleTheme = () => {
        setTheme((currentTheme) =>
            currentTheme === "light" ? "dark" : "light"
        );
    };

    const contextValue = {
        theme,
        toggleTheme
    };

    return (
        <ThemeContext.Provider value={contextValue}>
            {children}
        </ThemeContext.Provider>
    );
};
```

Обновление сделано через функцию, а не через готовое значение. Это важно, если несколько обновлений состояния окажутся в одной очереди: функция получает актуальное предыдущее значение, а не то, которое было на момент рендера.

Хук `useTheme` просто скрывает `useContext` за понятным именем:

```jsx
export const useTheme = () => {
    return useContext(ThemeContext);
};
```

В `main.jsx` провайдер оборачивает все приложение:

```jsx
<ThemeProvider>
    <App />
</ThemeProvider>
```

Поэтому и кнопка, и карточки работают с одним и тем же состоянием.

## Карточки и их поведение

Каждая карточка получает свойство `variant`. От него зависит, какую тему показать:

```jsx
function getCardTheme(variant, pageTheme) {
    if (variant === "fixed") {
        return "light";
    }

    if (variant === "opposite") {
        return pageTheme === "light" ? "dark" : "light";
    }

    return pageTheme;
}
```

| Карточка | Вариант | Светлая тема страницы | Темная тема страницы |
| --- | --- | --- | --- |
| Глобальная тема | `global` | светлая | темная |
| Фиксированная тема | `fixed` | светлая | светлая |
| Противоположная тема | `opposite` | темная | светлая |

Цвета карточки берутся из тех же CSS-переменных, что и у страницы. Когда карточке добавляется класс `light` или `dark`, переменные переопределяются внутри нее, и она перестает зависеть от темы родителя. Отдельные стили для каждой комбинации не нужны.

## Теоретическая часть

React это библиотека для построения интерфейсов из компонентов. Компонент получает данные через props и хранит собственное состояние через хуки. При изменении состояния React заново вызывает компонент и обновляет только те части DOM, которые действительно изменились.

JSX это синтаксис, который позволяет описывать разметку прямо в JavaScript. Он похож на HTML, но внутри фигурных скобок можно писать выражения, а атрибуты называются по правилам JavaScript, поэтому вместо `class` используется `className`.

Хуки это функции, которые дают функциональному компоненту возможности, раньше доступные классовым компонентам. `useState` добавляет состояние, `useContext` читает значение контекста. Хуки вызываются только на верхнем уровне компонента, их нельзя вызывать внутри условий или циклов, потому что React определяет их по порядку вызова.

Context API решает задачу передачи данных через несколько уровней вложенности. Без него тему пришлось бы передавать через каждый промежуточный компонент, даже если он сам ее не использует. Провайдер кладет значение в контекст, а любой потомок может прочитать его через `useContext`.

CSS-переменные это значения, которые объявляются в одном месте и используются через `var()`. Они наследуются по дереву DOM, поэтому смена класса на контейнере меняет цвета всех элементов, которые ссылаются на эти переменные. Для тем это удобнее, чем дублировать правила для каждого селектора.

## Ответы на вопросы

В методичке контрольных вопросов нет, поэтому вопросы составлены по теоретической части.

**1. Зачем нужен Context API, если данные можно передать через props?**

Props передаются только вниз и только явно. Если тема нужна в глубоко вложенном компоненте, ее придется протащить через все промежуточные компоненты, даже если они ее не используют. Контекст позволяет потомку прочитать значение напрямую. При этом контекст не заменяет props полностью: данные, которые нужны только одному компоненту, проще передать обычным свойством.

**2. Что делает createContext и что будет, если вызвать useContext вне провайдера?**

`createContext(defaultValue)` создает объект контекста с запасным значением. `useContext(ThemeContext)` возвращает значение ближайшего провайдера. Если провайдера нет, вернется значение по умолчанию. В этом приложении это `light` и пустая функция, поэтому кнопка вне провайдера ничего бы не делала.

**3. Почему в toggleTheme используется функция-обновление setTheme?**

Новое значение зависит от предыдущего. Запись `setTheme(currentTheme => ...)` гарантирует, что React передаст актуальное значение на момент обновления. Если бы использовалось `setTheme(theme === "light" ? "dark" : "light")`, функция замкнулась бы на значение из текущего рендера, и при нескольких подряд обновлениях результат мог бы оказаться неверным.

**4. Чем состояние useState отличается от обычной переменной?**

Обычная переменная не сохраняется между рендерами и не вызывает новый рендер при изменении. `useState` возвращает текущее значение и функцию установки. Вызов функции установки сообщает React, что состояние изменилось, и компонент перерисовывается с новым значением.

**5. Как переключение темы связано с CSS-переменными?**

В `index.css` объявлены два набора переменных, `.light` и `.dark`. Корневой элемент получает класс текущей темы, поэтому все дочерние элементы наследуют нужные значения. При переключении меняется класс, браузер пересчитывает цвета, а CSS-переходы сглаживают изменение.

**6. Почему карточка с фиксированной темой не меняется?**

`ContentCard` вычисляет класс карточки по свойству `variant`. Для варианта `fixed` всегда возвращается `light`, поэтому карточка получает светлый набор переменных независимо от темы страницы. Глобальная тема на нее не влияет.

**7. Как карточка с противоположной темой узнает, какую тему показывать?**

Она читает глобальную тему через `useTheme` и возвращает противоположное значение: `light` превращается в `dark`, а `dark` в `light`. Это делает та же функция `getCardTheme`, которая обрабатывает все три варианта.

**8. Что произойдет, если обернуть в ThemeProvider только часть приложения?**

Компоненты внутри провайдера будут работать с общим состоянием и переключаться вместе. Компоненты снаружи получат значение по умолчанию и не будут реагировать на кнопку. Поэтому провайдер стоит на самом верхнем уровне, выше `App`.
